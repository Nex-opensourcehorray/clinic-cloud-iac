## Lambda network-placement decision

The initial intake Lambda remains outside the VPC. The public intake layer has
no approved need for FSx, RDS, Directory Service, or clinical-system access.
Keeping it outside the VPC avoids NAT and interface-endpoint dependencies and
prevents accidental reuse of the existing broad clinic security group.

Any future clinical-system integration must use a separate, explicitly
constrained adapter with its own network and IAM decision.

## Proposed trust and data flow

```text
Browser
  -> Vercel server
  -> AWS WAF
  -> Regional API Gateway REST API
  -> intake Lambda
  -> DynamoDB nonce/idempotency/request state
  -> SQS Standard work queue
  -> worker Lambda
  -> future controlled clinical adapter
  -> reconciliation or receptionist exception workflow
```

The HMAC secret remains server-side. Requests are data-minimized, validated at
the public boundary and application layer, and accepted asynchronously with a
nonclinical correlation/request identifier. No request is represented as a
confirmed appointment until the authoritative system confirms it.

## HMAC model

- HMAC-SHA-256 over a versioned canonical request.
- Canonical inputs include method, normalized path/query, content type, exact
  body digest, timestamp, nonce, idempotency key, and key identifier.
- Initial timestamp tolerance is plus or minus five minutes.
- Signature comparison must be constant-time.
- Verification occurs before nonce reservation, idempotency processing, or
  business side effects.
- Key rotation uses explicit key identifiers and a short current/previous-key
  overlap.
- Secret values must not enter source code, logs, Terraform variables, plans,
  or state.

Production HMAC verification is deferred to W3.3.

## Nonce, replay, and idempotency design

DynamoDB is authoritative for workflow state using data-minimized namespaces:

```text
NONCE#<key-id>#<nonce>
IDEMPOTENCY#<key-id>#<idempotency-key>
REQUEST#<request-id>
```

Nonce and idempotency creation use conditional writes. Nonces receive a short
TTL covering the replay window. Idempotency records initially use a seven-day
TTL and store a request digest and workflow state rather than the request body.
A reused idempotency key with a different digest is rejected as a conflict.
Lambda ephemeral memory is not an acceptable replay or idempotency store.

## SQS, DLQ, and exception workflow

- SQS Standard decouples public intake from processing.
- DynamoDB idempotency accounts for at-least-once delivery.
- A DLQ is mandatory for exhausted worker retries.
- Transient worker failures retry through SQS.
- Downstream outages, partial processing, and unknown outcomes enter
  reconciliation and may require a receptionist exception workflow.
- A reconciler detects stale workflow states and prevents silent loss between
  durable state creation and queue delivery.

## Logging and monitoring design

- WAF, API Gateway, Lambda, SQS, DynamoDB, and reconciliation telemetry are
  required.
- Structured logs contain correlation IDs, state transitions, error classes,
  durations, and queue attempt metadata only.
- Request bodies, signatures, secrets, tokens, contact details, credentials,
  and clinical data must not be logged.
- Required alarms include API/Lambda failures, throttles, authentication and
  replay anomalies, stale requests, queue age, and any DLQ message.
- Log retention, redaction, and encryption are explicit configuration rather
  than defaults.

## Security findings carried into implementation

- **BLOCKER:** No public or uncontrolled direct access to a clinical database,
  FSx, Directory Service, or the authoritative clinical system is permitted.
- **MUST FIX BEFORE IMPLEMENTATION:** The existing clinic security group must
  not be reused by Wave 3.
- **MUST FIX BEFORE IMPLEMENTATION:** Separate least-privilege execution roles
  and scoped resource policies are required.
- **MUST FIX BEFORE IMPLEMENTATION:** Replay and idempotency controls must use
  atomic conditional writes rather than check-then-write behavior.
- **MUST FIX BEFORE IMPLEMENTATION:** Logs and traces must exclude request
  payloads and sensitive authentication or clinical data.
- **DESIGN CONSTRAINT:** WAF provides filtering and rate controls, not request
  authentication or business authorization.
- **DESIGN CONSTRAINT:** The profile alias `<READ_ONLY_AWS_PROFILE>` maps to an
  Operator/Administrator-named SSO context; least-privilege scope is not
  independently proven.
- **FOLLOW-UP:** Define final retention, KMS, backup, recovery, and manual-intake
  requirements before production readiness.

## Approved W3.2 architecture decisions

1. Use a Regional API Gateway REST API.
2. Keep the initial intake Lambda outside the VPC.
3. The public intake path must not directly access FSx, RDS, Directory Service,
   or the authoritative clinical system.
4. Use asynchronous `202 Accepted` semantics.
5. Use DynamoDB as the authoritative nonce/replay and idempotency store.
6. Use an SQS Standard work queue.
7. Create a DLQ.
8. Use an initial seven-day idempotency TTL.
9. Use the accepted HMAC-SHA-256 design.
10. Never place HMAC secret values in Terraform state.
11. Use separate least-privilege Wave 3 IAM roles.
12. Do not reuse `Clinic-NonProd-Group`.
13. Use a separately constrained adapter for future clinical integration.
14. Keep Codex AWS commands subject to explicit per-command manual approval.
